API Design in the Era of LLMs

Why interface stability has quietly become a correctness property

This is an opinion piece. It argues a position I have held while building funcml, and which the last two years of coding assistants have only sharpened: the stability of a public interface is no longer a matter of politeness to your users. It is now part of whether your software is correct in practice.

The claim

A library has two audiences. The first is the person who reads the documentation today and writes code against the current version. The second, new and now enormous, is every language model trained on the accumulated public record of how your library was used across all of its previous versions. The second audience does not read your changelog. It cannot tell a current idiom from one you deprecated four years ago. It reproduces whatever pattern appeared most often in its training data, with full confidence and no version awareness.

If your API has been stable, those two audiences receive the same answer. If your API has churned, the model becomes a machine for emitting code that no longer runs, or worse, code that runs but no longer means what it used to.

Interface stability used to be a usability feature. In the era of LLMs it is closer to a correctness guarantee, because a large fraction of the code written against your library will now be generated by a system whose knowledge is a weighted average of your entire history rather than a snapshot of your present.

What actually changed

Three things happened at once.

Generation replaced recall. A few years ago a user stuck on your API searched, read a few results, checked the dates, and adapted. The reader did version reconciliation in their head. Now the user asks a model and pastes the answer. The reconciliation step is gone, and the model does not perform it.

Training data is dominated by the past. The public corpus for any successful library is heavily weighted toward its early, most-discussed years. Every superseded function call, every retired argument, every old evaluation convention is still indexed, still upvoted, still sitting in a tutorial that was never updated. Volume of documentation does not fix an unstable API. It embalms every previous state of it as competing, undated advice.

Confidence is decoupled from currency. A stale forum post at least carries a date. A model’s answer carries none. It presents a deprecated idiom with exactly the same fluency as a current one. The user has no signal that anything is wrong until the code fails, and if the code merely changed behaviour rather than breaking, they may get no signal at all.

The net effect: the larger and older the body of writing about a moving API, the more reliably a model will hand a newcomer code that is subtly wrong. That is an uncomfortable inversion of the usual assumption that more documentation is better.

A methodology

What follows is the set of rules I try to hold myself to. None of them are novel. The argument is only that the cost of violating them has gone up.

Keep the surface small and orthogonal. A handful of verbs that compose beats fifty specialised functions. fit, evaluate, tune, cv, compare, interpret, estimate. Fewer entry points means fewer things to describe, fewer things to get wrong, and fewer things that can drift. A small surface is also a surface a single person can hold in their head, which is the only kind that stays coherent over years.

Own your contracts. Decide yourself what a fitted object contains, what predict returns, how a factor outcome is handled, what a probability column looks like. If those decisions are delegated to a stack of upstream packages, then every upstream design change becomes a change in your behaviour that you did not make and cannot veto. Owning the contract is what lets you promise it will not move.

Prefer shallow dependencies made of stable parts. Calling ranger, glmnet, xgboost, and the base stats model functions directly means each dependency is a small, single-purpose package with an interface that has barely moved in a decade. Building instead on a large, coordinated ecosystem means signing up to track that ecosystem’s lifecycle in perpetuity. Both are dependencies. Only one of them is a standing maintenance obligation.

Treat deprecation as a failure, not a feature. A formal deprecation process is honest, and long warning windows are considerate, but a deprecation is still an admission that the interface was wrong and that every downstream user must now do work. For an infrastructure library the correct target rate of breaking changes is close to zero. If you import a package that deprecates on a regular cadence, you have inherited that cadence.

Write documentation that ages well. Favour examples that exercise the stable core over examples that show off a clever new argument. Date your posts. When you must show an old and new way, label them unmistakably. Assume a model will ingest the page with no context and reproduce whatever it sees.

Make formulas and plain data the interface. A standard R formula and a data frame are the most stable contract in the language. An API expressed in those terms inherits their permanence. An API expressed in bespoke specification objects inherits their churn.

The critique

The pattern I am most wary of is the wrapper built on a wrapper: a convenience package whose value proposition is a simple front door, sitting on top of a deep, coordinated stack of other packages that are themselves still evolving.

The appeal is obvious. You get breadth quickly, you inherit a large community’s testing, and the individual pieces are often genuinely well made. But the reliability of the result is not something the author controls. It is the union of the failure modes of every layer. A change in low-level evaluation semantics, a reordering of columns by a preprocessing step, a shifted default in a parameter package, any of these can surface as a wrong answer from the top-level function, and the author of that function can only wait or work around it.

You can see the shape of this in the release history of such packages: many releases in a short window, most of them not adding capability but correcting core behaviour that turned out to be wrong, or repairing something an upstream change broke. That is not a package hardening on a solid base. It is a package discovering that its base keeps moving. Counting releases as evidence of maturity gets this exactly backwards.

Automated machine learning wrappers are especially exposed here, because their whole purpose is to hide the stack. When the hidden stack shifts, the user has no mental model with which to notice, and the LLM they ask for help has been trained on years of the stack’s older shapes. The abstraction that was supposed to protect the newcomer becomes the thing that prevents them from seeing what went wrong.

None of this is an argument against large ecosystems as such. They are a reasonable place to prototype and a fine place to learn concepts. It is an argument against putting one underneath a package whose entire pitch is durability and auditability, and then being surprised that the durability did not materialise.

A philosophical view

Underneath the practical argument there is a question about what we think software is.

One view treats a library as a living thing. It grows, it sheds old skin, it follows the best current understanding of how the problem should be modelled, and users are expected to move with it. Deprecation is the metabolism of a healthy project. On this view the accumulated old code in the world is just dead cells, and it is not the project’s concern that a language model keeps reanimating them.

The other view treats a published interface as closer to a promise, or even a small piece of public infrastructure. Once other people build on it, its shape is no longer entirely yours to revise. Base R holds this line: lm, predict, model.matrix have meant the same thing for decades, and that constancy is precisely what has allowed a whole scientific literature of reproducible code to accumulate on top of them. The value is not in the elegance of any one function. It is in the fact that code written against them in 2005 still runs and still means what it meant.

I hold the second view, and the arrival of code-generating models has made me hold it more firmly. We are now writing interfaces that will be consumed, at scale, by systems with no sense of time. Everything we ship becomes training data. A stable, modest, self-owned API is a small act of consideration toward a future in which most of the code calling your library was written by something that learned your library from its past.

The craftsman’s instinct to build something that lasts, and to keep its parts few and its joints visible, was always partly aesthetic. It now has a second justification. In a world where the dominant reader of your code is a model averaging over your history, the most useful thing you can do is not have much history to average over. Build it small, own every joint, and let it sit still.
